  ## "Good enough" is a false signal

  I keep several things running at once: a data annotation business, a data analysis shop that is preparing to launch, a few WeChat accounts, a survey system under development, and a set of handbooks I assembled myself. Every one of them moves. None of them moves all the way.

  For years the explanation I had for that state was not enough energy. The explanation turned out to be wrong. The awkward part was that I had no standard for deciding which thing should move on and which thing should stop. Without a standard a person picks the easiest thing: rewrite the document, adjust the interface, look up more material, think about it some more.

  In recent years I replaced the question "may this move on" with four questions that can be answered on the spot. Four gates, one at a time.

  I used to judge by activity: code changed yesterday, three rounds of discussion this week, two thousand words of documentation. Any movement counted as progress.

  That way has two holes.

  Movement can be unlimited. A thing can be reworked for half a year, changed every day, and never used by another person once. Editing code, editing wording, editing colours: all of it produces the feeling of being in progress.

  On the other side, the closer a thing gets to delivery the easier it is to polish in place. The last stage has the smallest changes and the fastest feedback, so it gets touched again and again.

  So I replaced the question with this one: what can this thing show another person right now.

  If there is something to show, move on. If there is not, go back and fill it in. The question does not care whether I am tired, whether I feel like it, whether I have inspiration. It only asks whether there is a thing.

  The four gates were first set up for projects done with AI, to stop it writing carelessly and skipping steps. After a while it became clear that the one being governed was mostly me.

  ## First gate: can the direction be explained to someone outside the trade

  The first gate covers the opening stretch. Passing it requires all of these:

  - A charter document that states what the thing is, who uses it, what problem it solves, what the first version does, and what the first version does not do.
  - A feature list walked through from three angles: roles, business flow, modules.
  - A stage plan whose first stage is the smallest version that runs the core flow.
  - A stack note that says why this choice, and why not the other three common options.
  - An architecture document that fixes directory rules, interface rules, error handling.
  - A rules file for the AI, containing prohibitions and acceptance criteria.

  The test is simple: find someone who does not work in this trade and talk for three minutes. If they ask "how is this different from XX", the difference has not been made clear. If they nod and say "got it, so it is the thing for whoever", the gate is passed.

  I have stuck on this gate many times, always in the same way: treating "we discussed it" as "we have it". Three hours of talking with an AI, everything perfectly clear in my head, not one file written. Next session starts empty, so the clarity is void, and the talk starts over and comes out slightly different.

  So I added a rule: no matter how clear the discussion, no file means nothing. The files are for the next version of me, and they are for the AI. An AI does not remember yesterday; it can only read what is in front of it today.

  ## Second gate: did it actually run once

  The second gate covers the skeleton, and the requirement is that several separate things each work once.

  - The frontend starts, the home page opens, and the colours, type sizes and spacing from the design spec are live.
  - The database connects, tables get created, a row goes in, a row comes back out.
  - Four backend lines work: the service starts, a sample endpoint responds, business logic writes one real record, logging and error handling behave.
  - The frontend calls the backend successfully: cross-origin (whether the browser may request the backend at all), response shape, and failure cases all line up.

  The only evidence for this gate is commands and output. One start gives one log; one query gives one result set.

  What this gate stops is "designed completely, never run once". I had a long stretch of that: architecture documents getting more detailed by the week, directory plans, error codes, log levels, permission entry points all thought through, and not one line executed. The world inside a document stays tidy because it has not met anything real.

  The problems a single real run produces are mostly absent from the design: port already taken, timezone mismatch, field type disagreement, cross-origin blocked, connection pool too small. Those only surface by running. No amount of documentation replaces that one start.

  ## Third gate: does the core path go end to end

  Once the skeleton runs, features get added one by one. This gate wants the whole path walked, and it wants nothing else broken by the walk.

  - All P0 features (the part the first version must have) are done.
  - Every development round leaves an acceptance record with command, output and log.
  - The full path runs from the first step to the last, each step really connected.
  - Neighbouring features are regression checked, not broken by this round.
  - Permission and input validation are examined: who may call this endpoint, what an over-privilege request returns, whether user A can reach user B's data.
  - Key operations leave logs.

  Judge by the path, not by the endpoints. Each endpoint returning 200 is easy; one path from the first step to the last is hard, because somewhere inside it you meet state, permissions, data ownership and failed rollbacks.

  My usual shape on this gate is "half the demo works". The first half is clickable, the second half is next week. Next week something else jumps in and the second half stays there forever. A demo needs one watchable stretch; a product needs the entire line.

  ## Fourth gate: is anyone really using it

  The last gate asks the hardest question: is someone using it, has it produced one real result.

  Four things are needed:

  - The pre-release overall check has no blocking issue.
  - It actually went live.
  - A retrospective was written.
  - At least one lesson from this round was written back into my own tool library.

  The third and fourth are additions I made myself. Without a retrospective the next project steps in the same hole; without writing back, this round's lesson stays only in memory and is gone in two months.

  This gate is the hardest because it requires other people. The first three gates I can satisfy alone in front of a screen. This one needs someone to actually come in, actually use it, actually pay once, or actually take away one deliverable. Whether other people take part is not my call.

  So it is also the gate I have skipped most often, and the skipping looks respectable: the project is still being finished, wait for the slow season, wait until this interaction is better. I have said these things to myself many times. Each time they hold up, and each time the effect is the same: the thing sits between the third gate and the fourth.

  ## What the gates really stop is skipping

  Laid out in a row, the four gates stop the same movement: jumping from an idea straight to polishing.

  Walking the whole sequence costs three kinds of pain. Explaining means getting questioned. Running means handling errors. Handing it to someone means hearing "this is not what I pictured". None of those three produce good-looking feedback.

  Polishing produces feedback, and immediately. Nudge the interface and it looks better at once; revise the document and it reads tidier at once. Without a standard for judging, a person automatically takes the path that pays feedback. A year can pass that way with nobody stopping, and it looks like being busy.

  The gates exist to block that path. Want to change the interface: first ask whether the skeleton runs. Want to improve the experience: first ask whether anyone uses it. These two questions are a buzzkill, and they saved me from a lot of redecorating inside the third gate.

  ## The order cannot be swapped

  I also tried the shortcut: simplify the early gates and charge straight at the last one. I tried it, and the cost doubled.

  Move on without the first gate and every later round changes direction. The AI writes a pile of files against a vague direction; when the direction changes, all of them are rework, and during rework you cannot tell which few are still usable.

  Add features without the second gate and the problems pile up until integration day, then appear together. Fields, permissions and response shapes all disagree, and one bug takes ten places to trace.

  Ship without the third gate and the first real use becomes the first real test. Lucky, you lose one user. Unlucky, you lose a batch.

  The gates have an order. While an earlier one is unpassed, the later ones do not count. Risk accumulates: a gap left early gets amplified downstream.

  Gates can also be papered over. To pass the first gate, write six files of two empty pages each: apparently complete, actually nothing. I have written that kind of filler file myself.

  The way to judge is to interrogate the files. That line in the charter saying what problem is solved: does it survive three rounds of follow-up. That item in the feature list: can you say who uses it, what goes in, and which branch an error takes. Files that go empty after two questions were not written.

  ## The gates gave me one more thing: permission to stop

  I used to be unable to stop. Stopping meant admitting failure, so I preferred to keep moving, moving anything.

  Now there is a neutral way to say it: this gate is unpassed. The sentence does not judge me, it names what is missing. Missing files, write files. Missing one start, go start it. Missing users, go ask one person.

  That phrasing works better than both "I think it is nearly there" and "I think it is not ready". The first makes people celebrate early, the second makes people delay forever, and neither produces a next step. "This gate is unpassed, what is missing is a start log" produces a next step.

  ## How I use them now

  When I want to open a new direction I ask two questions first: which gate is it standing in front of right now, and how many of the four gates am I willing to pay.

  The answers often put the idea back down. One thought walking from zero to the fourth gate means writing files, getting it to run, walking the path, and finding the first person who uses it. Opening a direction used to cost nothing but imagination, so I opened many. Now I can see the price, so I open fewer.

  I used to think I was running several things in parallel. I was starting several things. After opening fewer, the ones in my hands actually began to move. What this system did is make me open less; it never made me faster.

  If I cannot say which gate a thing is standing in front of, it has not started. It has only been discussed.

我手上同时开着好几件事：数据标注的业务、一个准备上线的数据分析店铺、几个公众号、一个问卷系统的开发、一套自己攒的手册。每件都在动，每件都动得不太彻底。

前几年我给这个状态找的解释是精力不够。后来发现这个解释不准确。麻烦的地方在于我没有标准判断哪件事该往前走、哪件事该停。没有标准的时候，人会挑最容易的那件：改文档、调界面、翻资料、再想一想。

这几年我把「能不能往下走」这个问题，换成了四个能当场回答的问题。四道门，一道一道过。

## 「差不多了」是个假信号

我以前的判断方式是看状态：昨天改了代码，这周聊了三轮，文档写了两千字。有动静就算有进展。

这套方式有两个漏洞。

动静可以无限大。一件事可以改上半年，每天都有改动，一次都没被别人用过。改代码、改措辞、改配色，这些都能制造「在推进」的感觉。

另一头，越接近交付越容易原地打磨。最后阶段的界面和文案改动最小、反馈最快，所以最容易被反复摸。

所以我把问题换成了这一句：这件事现在能拿出来给别人看的东西是什么。

拿得出来，往下走。拿不出来，回去补。这个问法不管我累不累、想不想、有没有灵感，只管有没有东西。

四道门最早是给 AI 协作的项目设的，管它别乱写、别跳步。用了一段时间发现，被管住的主要是我。

## 第一道门：方向能不能讲给不懂这行的人听

第一道门管开头那一段。过门要凑齐这些：

- 一份立项文档，说清是什么、给谁用、解决什么问题、第一版做什么、第一版不做什么
- 一份功能清单，按角色、业务流程、模块三个角度都过一遍
- 一份阶段计划，第一阶段必须是能跑通核心流程的最小版本
- 一份选型说明，写清为什么用这套，为什么不选另外三个常见方案
- 一份架构设计文档，写清目录规则、接口规则、错误处理
- 一份给 AI 的规矩文件，内容是禁止事项和验收标准

判断方式很简单：找一个不做这行的人，讲三分钟。他如果问「这个跟 XX 有什么区别」，说明差异点没讲明白；他如果点头说「明白，就是给谁用的那个东西」，这道门就过了。

我在这道门上卡过很多次，卡的方式很固定：把「聊过」当成「有了」。和 AI 聊三个小时，脑子里非常清楚，一份文件都没写。第二天开新会话，这些清楚全部作废，重新聊一遍，聊出来的还不太一样。

后来我给自己加了条规矩：讨论得再清楚，没有文件就等于没有。文件是给下次的自己用的，也是给 AI 用的。AI 不记得昨天，它只读得到今天摆在面前的这几份东西。

## 第二道门：有没有真的跑起来一次

第二道门管骨架，要求是几件事各自跑通一次。

- 前端能启动，首页能打开，设计规范里的颜色、字号、间距已经生效
- 数据库能连上、能建表、能插数据、能查出来
- 后端四条线走通：服务能启动、示例接口能返回、业务逻辑能写进一条数据、日志和错误处理能用
- 前端能调通后端接口，跨域（前端能不能直接请求后端）、返回格式、出错场景都对得上

过门的证据只有命令和输出。启动一次给一次日志，查一次库给一次返回结果。

这道门拦的是「设计得很完整，一次都没跑」。我在这上面有过很长的沉迷期：架构文档越写越详细，目录规划、错误码、日志级别、权限入口全都想到了，一行代码没跑。文档里的世界很整齐，因为它还没碰上任何真实的东西。

跑起来一次会遇到的问题，基本都不在设计里：端口被占、时区不一致、字段类型对不上、跨域被拦、连接数不够。这些只能靠跑一次暴露。文档写得再详细，也换不掉那一次启动。

## 第三道门：核心流程能不能从头走到尾

骨架通了，接下来一个功能一个功能地加。这道门要的是完整路径走通，还要走通之后没把别的弄坏。

- 所有 P0 功能（第一版必须有的那部分）做完
- 每一轮开发都有验收记录，拿得出命令、输出、日志
- 完整路径从头走到尾，从第一步到最后一步，每一步真实调通
- 相邻功能回归过，没被这一轮的改动弄坏
- 权限和输入校验查过：这个接口谁能调、越权访问返回什么、用户 A 能不能拿到用户 B 的数据
- 关键操作留下了日志

判断的时候看路径，不看接口。接口各自返回 200 很容易，一条路径从第一步走到最后一步很难，中间会碰状态、权限、数据归属、失败回滚这些真问题。

我在这道门上最常见的样子是「演示得了一半」。前半段能点，后半段说下周补。下周有别的插进来，后半段就一直停在那里。演示只需要一段能看的路径，产品要一整条。

## 第四道门：有没有人真的在用

最后这道门问的是最不好答的问题：有没有人在用，有没有产生一次真实结果。

过门要四样：

- 上线前的整体检查没有阻断性问题
- 真的上线了
- 复盘写过一遍
- 这次的踩坑至少有一条写回了自己的工具库

第三样和第四样是我自己加的。不写复盘，下一个项目会把这次的坑再踩一遍；不回写工具库，这一次的经验只留在记忆里，过两个月就没了。

这道门最难，因为它必须有别人参与。前面三道门我一个人对着屏幕就能交证据，这一道要有人真的点进来、真的用一次、真的付一次钱，或者真的拿走一份交付物。别人参不参与，我说了不算。

所以它也是被我跳过次数最多的一道。跳过的方式特别体面：项目还在完善、等淡季、等把这个体验再改改。这些话我对自己说过很多遍，每一遍都成立，每一遍的效果都一样，事情停在了第三道门和第四道门中间。

## 四道门真正拦的是跳步

把四道门排在一起，能看清它们拦的是同一个动作：从想法直接跳到打磨。

完整走一遍要吃三段苦。讲清楚要被人追问，跑起来要处理报错，给人用要听「这跟我想的不一样」。这三段都没有好看的反馈。

打磨有反馈，而且马上就来。界面调一下立刻好看，文档改一遍立刻整齐。人在没有判断标准的时候，会自动走有反馈的那条路。走一年也没人拦，看上去一直在忙。

门要做的事就是把这条路堵住。想改界面，先问骨架跑起来没有；想优化体验，先问有没有人用。这两个问题很扫兴，它们让我少花了不少时间在第三道门里面装修。

## 顺序不能换

我自己也想过：前面几道简化处理，直接冲最后一道行不行。试过，代价是加倍的。

第一道门没过就往下走，后面每一轮都在改方向。AI 按模糊的方向写出一堆文件，方向一改，这些文件全部返工，返工的时候还分不清哪几份能用。

第二道门没过就开始加功能，问题会堆到联调那天一起出现。字段、权限、返回格式全对不上，查一个问题要翻十处。

第三道门没过就上线，第一次真实使用会变成第一次测试。运气好的丢一个用户，运气不好的丢一批。

四道门有先后，前面一道没过，后面的都不算数。风险是累积的，前面留的缺口会被后面放大。

门也能被糊过去。为了过第一道门，写六份文件，每份两页空话，看起来齐全，实际什么都没有。这种凑数的文件我自己写过。

判断的办法是拿文件去提问。立项文档里那句「解决什么问题」，能不能被追问三轮还站得住；功能清单里那个功能，能不能说清给谁用、输入什么、出错走哪条路。问两轮就空的，等于没写。

## 门还给了我一样东西：停下来的许可

以前我停不下来。停对我来说等于承认失败，所以宁可继续动，动什么都行。

现在有个更中性的说法：这道门没过。它不评价我，说的是缺哪样东西。缺文件就去写文件，缺一次启动就去启动，缺用户就去问一个人。

这个说法比「我觉得差不多了」和「我觉得还不行」都好用。前一句让人提前庆祝，后一句让人无限拖延，两句都给不出下一步。「这道门没过，缺的是启动日志」有下一步。

## 我现在怎么用它

想开一个新方向的时候，我先问两个问题：它现在站在第几道门前？四道门我打算付几道？

这两个问题的答案经常让我把方向放回去。一个想法从零走到第四道门，中间要写文件、要跑起来、要走通路径、要找到第一个用的人。以前开新方向不花成本，只花想象力，所以开得很多。现在能看出代价，开的就少了。

我以前以为自己是在多线并行，其实是在多线开头。开得少了之后，手头那几件反而开始动了。这套东西的效果是让我少开了几个，从来没让我变快。

如果一件事我说不清它现在在第几道门前，那它还没有开始，只是被谈论。
