  ## First, the folders

  The five levels are not a difficulty ranking. They say where a thing sits.

  - The inbox does one job: throw it in. No sorting, no classifying. It carries its own test as well — anything untouched for two weeks probably was not important.
  - The incubating stage gets a validation card and a time box. Pass and it moves up, fail and it goes straight to the archive.
  - Active is where the real work happens.
  - The asset library extracts what is reusable while the project is still running, not after. The line in my own ledger reads: wait until the project ends and you will most likely have forgotten.
  - The archive gets a summary card and keeps the option of being reopened. Archiving is not deleting.

  What actually holds me back is two numbers: no more than three ideas in incubation, no more than two or three builds running at once. Anyone can keep a to-do inbox full. What stops work from advancing is those two caps.

  ## Four gates across fourteen stages

  There are four gates, and fewer is not sloppiness. The charter gate covers stages 1 to 4, the architecture gate 5 to 10, the delivery gate 11 to 12, the release gate 13 to 14. Each gate is a checklist ticked item by item: 7 for charter, 7 for architecture, 8 for delivery, 7 for release.

  A few of the seven charter items felt like bureaucracy when I wrote them:

  - The charter document covers 8 required contents.
  - The feature list is broken down along three axes: roles, business flow, modules.
  - The first stage of the plan must be an MVP — no making the first milestone the complete system.
  - The stack decision gives exactly one recommendation and records why the rejected options were rejected.
  - The architecture document lands: directory structure, interface rules, error handling.
  - The constitution for the AI lands, and in a location the editor actually reads.
  - At least four Git commits, with a .gitignore in place.

  No gate may be skipped. No architecture before the charter passes, no business code before the architecture gate, no talk of release before the delivery gate. In my constitution it is one sentence: one gate, one verification.

  Advancing state carries five hard constraints, two of which are orders I gave myself.

  - Without evidence, nothing may be marked passed. Every acceptance item must produce a file path, a command output or a screenshot.
  - An unverified item must be written as unverified. Writing it as basically done is not allowed.

  Basically done is a phrase I put on the banned list. It lets you off two things at once: saying how far it actually goes, and admitting what is still missing.

  ## Running it on myself

  This site opened its repository on 17 July 2026 and passed the charter gate in August: charter, stack decision, architecture document and the Agent constitution all landed, five Git commits, all 7 charter items ticked — only then was the architecture gate allowed to open.

  After that the system started paying interest. The site keeps a pit log with five entries, each carrying a field asking whether the lesson was written back into the rules; all five say yes. Three of them:

  - The share card generated fine locally, but the site CI produced had no such image. Cause: a missing leading slash in .gitignore made the pattern images/ also swallow the deployment asset folder. Written back as a rule: any new static asset gets checked once with git check-ignore -v.
  - I looked at the serif type scale and thought it held. Visitors saw system fallbacks. Cause: the judgement came from my own development machine — the source font installed locally, and localhost always reachable. Written back as a rule: visual acceptance must separate my machine from a visitor machine.
  - The font subsetting script was always right on my machine and failed the first Actions run after a push. Cause: it derived the repository root by stripping the leading slash off a pathname, which happens to work on Windows and becomes a relative path on Linux. Written back as a rule: resolve your own path with fileURLToPath, and when local is green but CI is red, suspect the platform-specific lines first.

  All three point at the same thing: I was not careless enough — I had picked the wrong surface to verify against.

  ## Gates the system never passed itself

  The other side has to be stated here. The root of the project system has no PROJECT_STATUS, no charter gate record and no changelog — the set of gates governing a dozen projects has never been walked by any gate itself. Further checks:

  - project-manual.md in the templates folder is a zero-byte file.
  - project-card.md, idea-validation.md and asset-card.md, all promised by the root README, do not exist on disk.
  - Apart from one work-log directory the asset library is nearly empty, and the archive holds no completed summary card.
  - In the gate table the architecture row lists its pass criteria with one item written twice.

  One more inconsistency in wording: an early visual-direction document of mine says the sequence has five gates, while the ledger has 4 gates and 4 cards — a feature gate and an implementation gate exist in no checklist file at all. This piece follows the ledger. Where rules rot is not usually in being unwritten but in the same thing looking different in two documents.

  (To be filled by me, one) The first time basically done fooled me: which year, what work, and how it ended.

  (To be filled by me, two) What I thought on finding the holes above — fix them, or leave them, and why.

  (To be filled by me, three) How many times I broke the caps of three in incubation and two or three in flight, and the one time I pushed forward without passing a gate: was it a good outcome or a bad one.

## 先说目录

五级不是难度分级，是东西放在哪儿。

- 收集区只做一件事：先丢进来。不整理、不分类。它自己写着另一条判据——超过两周不碰的东西，大概不重要。
- 孵化区要填验证卡、定周期。验证通过进下一层，失败直接进归档。
- 进行中是主力战场。
- 资产库在项目进行中就提取可复用的部分，不要等做完。台账里那句话是：等项目结束再提取，大概率忘了。
- 归档区写总结卡片，并且保留被重新捞起来的可能。归档不是删掉。

真正拦得住我的是两条数字：孵化中的项目不超过三个，同时开工的不超过两到三个。一个装满代办事项的收集区谁都有，能让事情停在下一层不动的，是这两条上限。

## 四道门，14 个阶段

门是四道，不是越多越好。立项门管阶段 1 到 4，架构门管 5 到 10，业务门 11 到 12，上线门 13 到 14。每道门一张检查清单，逐项打勾：立项门 7 项、架构门 7 项、业务门 8 项、上线门 7 项。

立项门的 7 项里，有几项一开始我觉得是形式主义：

- 立项文档要覆盖 8 项内容。
- 功能清单按角色、业务流程、模块三个维度拆一遍。
- 阶段计划的第一阶段必须是 MVP，不许把第一个里程碑就定成完整系统。
- 技术选型只给一个推荐，把淘汰掉的方案为什么淘汰也写下来。
- 架构设计文档落盘，含目录结构、接口规则、错误处理。
- 给 AI 的宪法落盘，而且要放在编辑器真会读到的位置。
- Git 至少四次提交，且建好 .gitignore。

门与门之间不许跨越。没立完项不画架构，架构门没过不写业务代码，业务门没过不谈上线。这条写在宪法里只有一句话：一门一验。

推进状态还有五条硬约束，其中两条是我给自己下的死命令。

- 没有证据，不许标记通过。每项验收必须给出文件路径、命令输出或者截图。
- 未验证项必须写「未验证」，不允许写「基本完成」。

「基本完成」这四个字是我列进禁词的。它同时免掉了两件事：说清楚做到了哪儿，和承认还差什么。

## 用在自己身上

这个站点 2026 年 7 月 17 日建仓库，8 月过立项门：立项文档、技术选型、架构设计、Agent 宪法四份落盘，Git 五次提交，立项门 7 项硬指标全部勾掉，然后才允许进架构门。

进架构门之后，这套东西开始收利息。站点有一份踩坑日志，五条坑每条都标了是否反哺成规矩，五条都是「是」。挑三条：

- 分享卡片在本地生成后一切正常，推上去之后 CI 检出的站点根本没有这张图。根因是 .gitignore 里 images/ 少了一个前导斜杠，连带挡住了部署资产目录。反哺的规矩：新增静态资源必须跑一次 git check-ignore -v 验一遍。
- 我目测衬线字号觉得成立，访客看到的却是系统回退字。根因是这个判断的依据来自开发机——本机装了源字体，而且 localhost 永远可达。反哺的规矩：视觉验收要分清「我的机器」和「访客的机器」。
- 字体子集脚本在我电脑上一直是对的，push 之后 Actions 第一次就报红。根因是脚本用 pathname 去掉首斜杠来推仓库根目录，Windows 下这个写法凑巧成立，Linux 下变成相对路径。反哺的规矩：拿自身路径一律走 fileURLToPath，「本地绿、CI 红」先怀疑平台相关的那几行。

三条坑指向同一件事：不是我不够小心，是我的验收面选错了地方。

## 这套体系自己没过的门

写到这儿必须交代反面。台账根目录没有 PROJECT_STATUS，没有立项门记录，也没有变更日志——也就是说，管着十几个项目的那套门禁，本身没走过一次门。再往下查：

- 模板目录里的 project-manual.md 是一个零字节空文件。
- 根 README 承诺存在的 project-card.md、idea-validation.md、asset-card.md，磁盘上都不存在。
- 资产库除了工作日志目录，近乎是空的；归档区里没有一张填写完整的总结卡片。
- 门禁总表里架构门那一行，过门标准把「真源文档有」写了两遍。

还有一处口径不一致：站点早期一份视觉方向的文档里我写过「五门是真序列」，而台账只有 4 道门、4 张门禁卡，「功能门」「实现门」在任何清单文件里都不存在。这篇文章以台账为准。规矩最容易坏掉的地方不是没写下来，是同一个东西在两份文档里长得不一样。

（待你口述 · 一）第一次被「基本完成」骗到是哪一年、什么活、那件事后来怎么收场。这一节只有你能写，我编了就等于整篇作废。

（待你口述 · 二）上面这几个窟窿你发现的时候是怎么想的：改，还是就这样放着，为什么。

（待你口述 · 三）孵化不超过三个、同时开工不超过两到三——这两条上限你破过几次；哪一次你选择不按门禁直接推进，结果是好的还是坏的。
